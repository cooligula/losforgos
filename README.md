# LineageOS Apps for GrapheneOS/AOSP

Material 3 apps from LineageOS, installable on any Android phone, alongside a patched version of Gcam Services Provider by [Lukas Pieper](https://github.com/lukaspieper) work properly with the Pixel Camera when the phone is locked. They are built from LineageOS's
source with GitHub Actions, signed with one stable key and published as GitHub releases that
[Obtainium](https://github.com/ImranR98/Obtainium) can install and update.

## Why this exists

Android systems without Google apps, such as GrapheneOS and other AOSP-based ROMs, ship the plain
AOSP apps: gallery, camera, dialer, clock and so on. They work, but many are dated and some are no
longer maintained. LineageOS maintains newer, Material 3 versions of most of them, but those only
come inside LineageOS: they are built as system apps with the platform build system, and under their
original names they would clash with the AOSP apps that are already on the phone.

This project is a free and open-source set of replacements for the stock AOSP apps:

- Each app is built from LineageOS's source, at a pinned and reviewed upstream commit.
- Each app gets its own application id (`org.losforgos.<name>`), so it installs next to the stock
  app instead of conflicting with it. Nothing is a system app and nothing needs root.
- Apps that LineageOS only builds with the platform build system (Dialer, Messaging, Contacts) are
  ported to Gradle so that they build as ordinary apps.
- Everything is signed with one key, so updates install in place and Obtainium can follow them.

On top of that, a few apps are also released as a *modified* variant with a security or privacy
improvement that upstream does not have. The unmodified build is always published too. See
[What we added](#what-we-added).

## Install and update with Obtainium

Obtainium installs apps straight from GitHub releases and updates them when a new release appears.

## What we added

Everything here is in this repository as a patch in [`patches/`](patches/), a rule in
[`apps.toml`](apps.toml) or a file under [`ports/`](ports/). Each modified release also states its
difference in its release notes.

### Secure review: Glimpse and Gcam Bridge

**What it is.** On a locked phone you can open the camera from the lock screen and take photos without
unlocking. The gallery button in that camera does not open your whole library, which would defeat the
lock. It opens a "secure review": a gallery on top of the lock screen that shows only the photos taken
during this camera session, so you can check the shots you just took and nothing else.

**What was missing.**

- *Glimpse* already answers the secure review request, but Pixel Camera sends it only the last photo
  plus a list of the ids of the others. Upstream Glimpse ignores that list, so on the lock screen you
  can see just one photo. The modified Glimpse reads the list and shows every photo of the session,
  starting at the last one, still only on top of the lock screen.
- *Gcam Bridge* is [Gcam Services Provider](https://github.com/lukaspieper/Gcam-Services-Provider),
  which lets Pixel Camera (the Google camera app, installed separately) work on systems without Google
  apps. Pixel Camera opens the gallery by sending an intent to Google Photos, so Gcam Bridge installs
  under the Google Photos package name and passes the request on to a gallery you have. Upstream it
  only opens the last photo as a normal view, which does not work on a locked phone. The modified
  Gcam Bridge forwards the secure review request unchanged to a gallery that accepts it (Glimpse is preferred) and may show over the lock screen.

Together they give Pixel Camera on a de-Googled system the lock-screen review that Google Photos
provides on a stock Pixel. Glimpse also works as a normal gallery without Gcam Bridge. Both are
modified by default in Obtainium. Without Pixel Camera there is nothing to forward, so Gcam Bridge is
only useful with it.

The Glimpse variant also updates the ZoomImage library, which fixes the image jumping after a pinch
to zoom.

### Memory tagging: Aperture, Keyboard and Messaging

Memory tagging (MTE) is a hardware feature of recent phones (Pixel 8 and newer, GrapheneOS included)
that detects memory bugs in native code, the usual source of exploitable vulnerabilities. An app has to
opt in. The modified variants of the three apps that contain native libraries opt in with
`android:memtagMode="async"`: a real memory bug then crashes the app instead of silently corrupting
memory. On devices without memory tagging nothing changes. GrapheneOS Camera makes the same choice.
These variants are not the Obtainium default until they have been tested on a device with memory tagging.

### Private alarms: Clock

Upstream Clock accepts "snooze" and "dismiss" broadcasts (`com.android.deskclock.ALARM_SNOOZE` and
`ALARM_DISMISS`) from any app, so an app you installed could silently cancel your alarm. The modified
Clock no longer accepts these two from other apps, which is also what GrapheneOS did to its Clock in
2022. Android's standard alarm intents (set, snooze and dismiss through `AlarmClock`) are unchanged, so
other apps that set alarms keep working.

### Dialer

The Dialer is installed as `org.losforgos.dialer`, so it sits next to the system Dialer. Set it as the
default phone app (Settings, Apps, Default apps, Phone app) to use it. Compared with LineageOS's Dialer:

- **Contact matching ignores the country prefix.** Android matches `612345678` and `+34612345678` by
  guessing the country, and often misses; on a phone with two SIMs from different countries no single
  guess works. The Dialer reads a number without a prefix as a national number of every country of the
  SIMs in the phone, and a number with a prefix as itself, then accepts a contact only if its stored
  number is the same number. The incoming call screen, the call log and the missed call notifications
  all use it. A number with an explicit different prefix never matches.

Limitations: no visual voicemail and no call recording, since both need system privileges, and
prefix matching does not cover the search box and smart dial yet.


## Verifying a download

Every release is signed with the same key and carries a build provenance attestation.

- Checksum: each release has a `.sha256` file next to the APK, and the APK's SHA-256 is in the release notes.
- Provenance: `gh attestation verify <apk> --repo cooligula/losforgos` confirms the APK was built by this
  repository's workflow.
- Signature: `apksigner verify --print-certs <apk>` prints the signing certificate. The release job
  refuses to sign unless the key matches the fingerprint stored in the repository variable `CERT_SHA256`,
  so every APK shows the same certificate. Android refuses to install an update signed with a
  different key over an installed app.

## How it works

- [`apps.toml`](apps.toml) pins one upstream commit per app. The `bump upstream` workflow opens a pull
  request on the 1st and 15th of each month when upstream moved.
- The `build` workflow fetches the pinned commit, renames the application id, sets a monotonic version
  (`versionCode = YYYYMMDDNN`), applies the patches for modified variants, and builds an unsigned
  release APK. This job has no access to secrets.
- The `release` job (only on `main`, in the `release` environment) signs the APKs, attests them, and
  creates one release per app and variant: tag `<app>-v<version>`, assets `<app>-<version>-<variant>.apk`
  plus a `.sha256`. An app is only released again when its build inputs changed.
- Native libraries and 16 KB page alignment are listed in each build log.
- The Obtainium badge, the per-app links, [docs/obtainium.html](docs/obtainium.html) and
  `obtainium-apps.json` are generated from `apps.toml`. After changing the app list, run
  `python3 scripts/losforgos.py deeplink --write`; the `plan` job of the build workflow fails when they
  are out of date (`deeplink --check`). The badge opens `docs/obtainium.html` through GitHub Pages
  (Settings, Pages, deploy from branch `main`, folder `/docs`), because Obtainium's public redirect page
  only accepts a single app and GitHub strips `obtainium://` links from this file.

## Building

CI is the supported way to build. To reproduce a build locally you need Python 3.11 or newer, git, the
JDK the app asks for (`java` in `apps.toml`), and the Android SDK with the NDK for apps with native code:

```sh
python3 scripts/losforgos.py fetch glimpse
python3 scripts/losforgos.py prepare glimpse --variant modified
bash scripts/build.sh glimpse
bash scripts/check-apk.sh dist/glimpse/*.apk
```

The unsigned APK ends up in `dist/<app>/`. To build in CI instead, run the `build` workflow manually
(`gh workflow run build.yml --ref main -f only=glimpse`); pull requests build every enabled app.

Patches are plain `git diff` output in `patches/<app>/NN-description.patch`; see
[patches/README.md](patches/README.md). A patch that stops applying fails the build, which is the signal
to rebase it.

### Releasing from your own fork

Run once in a clone of the repository, on macOS or Linux:

```sh
scripts/setup-signing.sh
```

It creates the signing key (openssl only, no Java), installs and logs in the GitHub CLI if needed,
creates the `release` environment limited to `main`, stores the signing secrets and the `CERT_SHA256`
variable, and allows Actions to open pull requests. Back up `~/.losforgos-keystore` and its password:
if the key is lost, every installed app has to be uninstalled before an update signed by a new key will
install. Then publish the first releases, and regenerate the Obtainium links for your repository:

```sh
gh workflow run build.yml --ref main -f release=true -f force=true
python3 scripts/losforgos.py deeplink --write
```
